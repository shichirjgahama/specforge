# Производительность и профилирование

Замеры выполнены на Python 3.14, Windows, 4-ядерный ноутбук, без GPU.
Скрипт: `bench/profile_specforge.py`. Сырые результаты:
`bench/results.json`, профиль: `bench/profile.txt`.

Воспроизведение:

```text
python bench/profile_specforge.py
```

## 1. Итоговые замеры

| Метрика | Лимит | Факт | Статус |
|---------|-------|------|--------|
| Парсинг DSL на 1000 строк | < 100 мс | 18.3 мс (1009 строк, 5196 токенов) | выполнен |
| Impact analysis, 174 узла, 60 тестов, 100 требований | < 1 с | 0.47 мс | выполнен |
| Полный прогон 60 тестов | < 10 с | 8.4 мс | выполнен |
| Инкрементальный пересчет одного требования | <= 5% узлов | 8 из 174 = 4.6% | выполнен |

## 2. Оптимизация 1: лексер

До: наивный сканер по символам, который для каждого токена заново считает
строку и столбец через `str.count` и `str.rfind`.

После: регулярные выражения только для идентификаторов и чисел, позиции
обновляются инкрементально при сдвиге, мультисимвольные операторы
проверяются по таблице.

| Вариант | Время, мс |
|---------|-----------|
| Наивный сканер | 27.11 |
| Оптимизированный лексер | 10.68 |
| Ускорение | 2.54x |

Фрагмент замера:

```text
optimization_1_lexer:
  naive_ms: 27.110
  optimized_ms: 10.681
  speedup: 2.54
  tokens: 5196
```

Профиль подтверждает: на 1000 строк лексинг занимает около 39 мс вместе с
созданием объектов токенов в профилируемом режиме, парсинг - около 40 мс
при накладных расходах cProfile. Без профилировщика 18.3 мс на файл.

## 3. Оптимизация 2: кэш обратного графа

До: при каждом запросе impact analysis обратный граф строится заново:
`O(V + E)` на запрос.

После: `SpecIndex.reverse` строится один раз и кэшируется; запрос
замыкания стоит `O(достижимые узлы + ребра)`.

| Вариант, 100 запросов | Время, мс |
|-----------------------|-----------|
| Обратный граф строится каждый раз | 4.345 |
| Кэшированный обратный граф | 0.303 |
| Ускорение | 14.34x |

Результаты обоих вариантов совпадают: бенчмарк проверяет равенство
множеств замыканий.

## 4. Профиль cProfile

Топ по cumulative time для полного прогона тестов, парсинга большого файла
и семантического анализа:

```text
272188 function calls in 0.096 seconds
   ncalls  tottime  cumtime  function
        1    0.000    0.079  parser.parse (1000 lines)
        1    0.000    0.040  parser.parse (demo spec)
      217    0.000    0.040  _parse_decl
        1    0.039    0.039  lexer.tokenize (1000 lines)
        1    0.027    0.027  runner.run_tests (60 tests)
       60    0.018    0.018  runner._run_one
      433    0.016    0.016  expression parsing
```

Горячие точки: лексинг большого файла и создание объектов токенов; на
рабочей спецификации (174 узла) доминируют парсинг и запуск симуляций.
Оптимизации выше снимают основную стоимость.

## 5. Почему тесты быстрые

- Симуляция не обращается к диску и сети.
- Каждый тест создает один `Simulation` из словаря записей, время
  виртуальное.
- Генерация тестов выполняется один раз и хранится в SQLite; повторный
  запуск читает готовые кейсы.
- 60 тестов - это 60 небольших сценариев по 1-5 операций.
- `cProfile` показывает 272 тысячи вызовов на весь прогон, что укладывается
  в миллисекунды.

## 6. Ограничения замеров

- Числа зависят от машины; в тестах используются широкие лимиты из
  задания, а не точные значения.
- cProfile добавляет накладные расходы, поэтому для лимитов берется
  обычный `time.perf_counter`, а профиль используется для поиска горячих
  точек.
- Лимит "4 ГБ ОЗУ" не проверяется отдельно: приложение не держит больших
  структур, пик памяти на демо-наборе - единицы мегабайт.
